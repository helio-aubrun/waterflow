# Waterflow — Documentation des incidents

# Incident #1

## Résumé

| | |
|---|---|
| **Titre** | Échec de 3 tests de non-régression sur un clone frais du dépôt |
| **Sévérité** | Mineure (n'affecte pas l'application en production, seulement la CI/les tests locaux) |
| **Statut** | Résolu |
| **Composant** | `tests/test_non_regression.py::TestMetriquesPerformance` |
| **Détecté via** | Exécution de la suite de tests complète (`pytest tests/ -v`) |

## 1. Détection et reproduction

En exécutant la suite de tests complète sur un clone fraîchement cloné du
dépôt (sans avoir préalablement exécuté le notebook d'analyse exploratoire),
3 tests échouent systématiquement avec la même erreur :

```
ERROR at setup of TestMetriquesPerformance::test_distribution_classes_stable
ERROR at setup of TestMetriquesPerformance::test_taille_dataset_stable
ERROR at setup of TestMetriquesPerformance::test_pas_de_valeurs_manquantes_dataset_clean

FileNotFoundError: [Errno 2] No such file or directory:
'.../data/water_potability_clean.csv'
```

**Reproduction** :

```bash
git clone https://github.com/helio-aubrun/waterflow.git
cd waterflow
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
pytest tests/test_non_regression.py -v
# -> 3 erreurs de setup (FileNotFoundError)
```

Le problème est reproduit à 100 % sur un environnement de développement
propre, sans dépendance à un état particulier de la machine.

## 2. Diagnostic — identification de la cause

Le fichier `data/water_potability_clean.csv` est un **fichier dérivé** : il
n'est pas la donnée source du projet (`data/water_potability.csv`, versionnée),
mais le résultat du pipeline de nettoyage exécuté dans le notebook
`notebooks/water_potability_eda.ipynb` (suppression des doublons, imputation
des valeurs manquantes par médiane conditionnelle, winsorisation des valeurs
extrêmes à 1 %/99 %).

Ce fichier est volontairement exclu du dépôt Git (`.gitignore` : *"Derived
data — regenerated by water_potability_eda.ipynb"*), un choix cohérent pour
ne pas versionner un artefact reconstructible. **Le problème** : la fixture
`dataset` de `TestMetriquesPerformance` (`tests/test_non_regression.py`, ligne
309-311) lit ce fichier directement par `pd.read_csv(...)`, sans vérifier son
existence ni le régénérer si absent :

```python
@pytest.fixture(scope="class")
def dataset(self):
    root = os.path.dirname(os.path.dirname(__file__))
    return pd.read_csv(os.path.join(root, "data", "water_potability_clean.csv"))
```

**Cause racine** : un contributeur qui clone le dépôt et lance directement
`pytest` (sans avoir au préalable ouvert et exécuté le notebook d'EDA dans son
intégralité) se retrouve avec 3 échecs de test sans rapport avec une
régression réelle de son code — un faux signal qui nuit à la fiabilité perçue
de la suite de tests et peut faire perdre du temps en investigation inutile.

## 3. Solution implémentée

Plutôt que de versionner le fichier dérivé (ce qui irait à l'encontre du choix
initial documenté dans le `.gitignore`) ou de supprimer les 3 tests concernés
(ce qui réduirait la couverture de non-régression), la solution retenue
régénère automatiquement le fichier manquant, en reproduisant fidèlement le
pipeline de nettoyage du notebook, via une fixture `autouse` ajoutée à
`conftest.py` :

```python
@pytest.fixture(scope="session", autouse=True)
def ensure_clean_dataset():
    root       = os.path.dirname(__file__)
    raw_path   = os.path.join(root, "data", "water_potability.csv")
    clean_path = os.path.join(root, "data", "water_potability_clean.csv")

    if os.path.exists(clean_path) or not os.path.exists(raw_path):
        return  # rien à faire : déjà présent, ou pas de source pour régénérer

    import pandas as pd
    from scipy.stats.mstats import winsorize

    df = pd.read_csv(raw_path).drop_duplicates()

    features     = [c for c in df.columns if c != "Potability"]
    missing_cols = ["ph", "Sulfate", "Trihalomethanes"]

    for col in missing_cols:
        medians       = df.groupby("Potability")[col].transform("median")
        global_median = df[col].median()
        df[col] = df[col].fillna(medians).fillna(global_median)

    df[features] = df[features].apply(
        lambda col: pd.Series(winsorize(col, limits=[0.01, 0.01]), index=col.index)
    )

    df.to_csv(clean_path, index=False)
```

Cette fixture, déclarée `autouse=True` et `scope="session"`, s'exécute une
seule fois avant le premier test de la session, indépendamment du fichier
lancé en premier — elle sécurise donc `test_non_regression.py` qu'il soit
exécuté seul ou dans la suite complète. Le nouveau paramètre `scipy` a été
ajouté à `requirements.txt` (dépendance nécessaire à `winsorize`).

### Pourquoi cette solution plutôt que les alternatives

| Alternative envisagée | Raison de l'écarter |
|---|---|
| Versionner `water_potability_clean.csv` | Contredit le choix de conception initial (fichier dérivé, reconstructible) ; alourdit le dépôt |
| `pytest.skip()` si le fichier est absent | Fait disparaître silencieusement 3 tests de non-régression réels au lieu de les exécuter |
| Régénérer manuellement via une commande documentée dans le README | Repose sur une action manuelle oubliable ; ne corrige pas la CI si l'étape est omise |
| **Régénération automatique via fixture `autouse` (retenue)** | Zéro action requise du contributeur, fonctionne identiquement en local et en CI, résultat strictement identique au notebook |

## 4. Vérification de la correction

```bash
rm -f data/water_potability_clean.csv   # simule un clone frais
pytest tests/ -v
```

**Résultat avant correction** : 190 tests passés, 3 erreurs de setup.
**Résultat après correction** : 193 tests passés, 0 erreur.

Le test a été rejoué à la fois en exécutant `test_non_regression.py`
isolément et dans la suite complète (`pytest tests/`), afin de vérifier que la
fixture `autouse` se déclenche correctement dans les deux cas de figure.

## 5. Versionnement de la solution

La correction (modification de `conftest.py` + ajout de `scipy` à
`requirements.txt`) est destinée à être committée sur une branche dédiée puis
intégrée via une pull request, avec un message de commit explicite
(`fix: régénération automatique du dataset dérivé manquant en test`),
conformément à l'amélioration de la granularité des commits déjà identifiée
comme axe de progrès du projet (cf. rapport E4, C16).

## 6. Impact et suivi

- Aucun impact sur l'application en production : le bug concernait uniquement
  l'exécution des tests en environnement de développement/CI, pas le
  comportement de l'API.
- La chaîne CI applicative (`.github/workflows/ci.yml`) bénéficie
  automatiquement de la correction, la fixture s'exécutant avant toute
  collecte de tests.
- Point de vigilance pour l'avenir : si le pipeline de nettoyage du notebook
  d'EDA évolue, la logique dupliquée dans `ensure_clean_dataset()` devra être
  mise à jour en miroir pour rester fidèle au notebook — un couplage à
  surveiller, documenté ici pour éviter une divergence silencieuse entre les
  deux implémentations.

# Incident #2

## Résumé

| | |
|---|---|
| **Titre** | JSON tronqué lors de la structuration OCR.space par Claude, sur un document réel |
| **Sévérité** | Mineure en pratique (le mécanisme de secours masque l'échec pour l'utilisateur final), mais dégrade silencieusement la performance et le diagnostic |
| **Statut** | Résolu |
| **Composant** | `api/services/ocr_service.py::_claude_structure()` |
| **Détecté via** | Appel réel du service avec les vraies clés API et un vrai document (`samples/fiche_non_potable_test.pdf`), pas un test avec mocks |

## 1. Détection et reproduction

En appelant réellement le service OCR (vraies clés `OCR_SPACE_API_KEY`/
`ANTHROPIC_API_KEY`, vrai fichier PDF), la cascade tombait systématiquement
sur le mécanisme de secours (Claude Vision direct) au lieu de réussir dès
le premier niveau (OCR.space + structuration Claude), avec ce message dans
les logs :

```
OCR.space échoué (Expecting ',' delimiter: line 15 column 4 (char 384)) — fallback Claude Vision
```

**Reproduction** :

```python
from api.services.ocr_service import extract_from_document
with open("samples/fiche_non_potable_test.pdf", "rb") as f:
    file_bytes = f.read()
result = extract_from_document(file_bytes, "application/pdf")
# -> log "OCR.space échoué..." puis succès via le niveau de secours (42s)
```

Reproduit à 100 % sur ce document réel, avant toute modification du code.

## 2. Diagnostic — identification de la cause

**Premier niveau de diagnostic (insuffisant)** : le message d'erreur
(`Expecting ',' delimiter`) provenait de `json.loads()` sur un extrait
obtenu par une regex gourmande :

```python
match = re.search(r"\{.*\}", clean, re.DOTALL)   # capture du 1er { au DERNIER }
```

Ce diagnostic était trompeur — il ressemblait à un JSON mal formé, mais
sans indiquer *pourquoi*. Une première correction (extraction par comptage
d'accolades équilibrées, `_extract_json()`, en ignorant les accolades à
l'intérieur des chaînes) a été apportée pour fiabiliser l'extraction — et a
immédiatement produit un message bien plus informatif :

```
OCR.space échoué (JSON incomplet (accolades non équilibrées) : {
  "date_prelevement": "2026-06-28", ...
  "Conductivity": 680.0) — fallback Claude Vision
```

**Cause racine réelle** : la réponse de Claude était **tronquée en cours de
génération**, pas malformée. `_claude_structure()` appelait l'API avec
`max_tokens=1024` — insuffisant, car le JSON de sortie doit inclure une
transcription intégrale (`raw_text`) en plus des mesures et avertissements ;
sur un document au contenu substantiel, la réponse dépassait cette limite
et s'arrêtait au milieu de la génération. La fonction sœur
`_claude_vision_extract()`, elle, utilisait `max_tokens=2048` et n'avait
jamais ce problème — ce qui a orienté directement vers la correction.

## 3. Solution implémentée

Deux correctifs, appliqués et vérifiés l'un après l'autre :

1. **`_extract_json()`** (nouvelle fonction partagée) : remplace la regex
   gourmande par un scan à accolades équilibrées, conscient des chaînes de
   caractères — utilisée par `_claude_vision_extract()` **et**
   `_claude_structure()`. Corrige le diagnostic, pas encore la cause racine.
2. **`max_tokens` porté à `2048`** dans `_claude_structure()` (aligné sur
   `_claude_vision_extract()`) — corrige la cause racine (troncature).

### Pourquoi ces deux correctifs plutôt qu'un seul

| Correctif seul | Résultat |
|---|---|
| Seulement `_extract_json()` | Diagnostic plus clair, mais la cascade continue à basculer inutilement vers le secours (bug masqué, pas résolu) |
| Seulement `max_tokens=2048` | Corrige ce cas précis, mais laisse la regex gourmande fragile face à un futur cas de troncature ou de JSON multi-blocs |
| **Les deux (retenu)** | Cause racine corrigée **et** robustesse de l'extraction améliorée pour des cas futurs non encore rencontrés |

## 4. Vérification de la correction

```bash
# Avant les deux correctifs
OCR.space échoué (Expecting ',' delimiter...) — fallback Claude Vision
Appel réussi en 42.60s

# Après _extract_json() seul (diagnostic amélioré, bug pas encore résolu)
OCR.space échoué (JSON incomplet (accolades non équilibrées)...) — fallback Claude Vision
Appel réussi en 41.22s

# Après les deux correctifs (résolu)
Appel réussi en 18.09s          # aucun fallback déclenché
mesures extraites : {'ph': 5.0, 'Hardness': 320.0, ...}   # identiques dans les 3 cas
```

Même document réel testé aux trois étapes, mesures extraites strictement
identiques à chaque fois — seul le chemin de la cascade change. Suite de
tests complète rejouée après coup : **214/214 tests passent**, aucune
régression (`pytest tests/ -q`).

## 5. Versionnement de la solution

Correction committée sur la branche principale, commit `f6471e3`
(vérifiable : `git show f6471e3 -- api/services/ocr_service.py`). Message de
commit non descriptif (`"ajout doc"`) — cohérent avec l'axe d'amélioration
déjà identifié pour la granularité des messages de commit (cf. rapport E4,
C16) ; une réintégration via une pull request avec un message explicite
(`fix: troncature JSON dans la structuration OCR (max_tokens insuffisant)`)
serait la pratique cible pour une prochaine correction de ce type.

## 6. Impact et suivi

- Impact utilisateur final nul au moment de la détection : le mécanisme de
  secours (Claude Vision direct) masquait l'échec et produisait un résultat
  correct — mais avec une latence 2,3× plus élevée (42s vs 18s) et un appel
  supplémentaire à un service tiers payant à chaque occurrence.
- Ce bug n'était visible dans **aucun test automatisé** avant cette
  vérification : `tests/test_api.py`/`test_e2e.py` mockent
  `extract_from_document`, donc n'exercent jamais le vrai chemin
  `_claude_structure()` (cf. échange précédent sur l'absence de test réel
  du service OCR). Seul un appel manuel avec de vraies clés API et un vrai
  document a permis de le détecter.
- Point de vigilance pour l'avenir : `max_tokens=2048` reste une valeur
  fixe, pas adaptative à la taille du document source — un document
  nettement plus long pourrait retomber dans le même type de troncature.
